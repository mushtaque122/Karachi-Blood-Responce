# Database — Foundation Phase

MongoDB, single `users` collection to start (donors/requests/etc. come
in later phases as their own collections, referencing `users._id`).

| Field | Type | Notes |
|---|---|---|
| `_id` | ObjectId | |
| `email` | string, unique, indexed | login identifier |
| `hashed_password` | string | bcrypt hash, never returned in API responses |

| `is_active` | bool | default true; account-disable switch (separate from lockout below) |

| `mfa_secret` | string or null | base32 TOTP secret (`pyotp`); generated by `/api/auth/mfa/setup`, not yet active until confirmed |

## `donors`
| Field | Type | Notes |
|---|---|---|
| `_id` | ObjectId | |
| `user_id` | ObjectId, unique, indexed | references `users._id`; one profile per user |
| `blood_group` | string enum | A+/A-/B+/B-/AB+/AB-/O+/O- |
| `city` | string, indexed | approximate location only — no exact address stored |
| `latitude`, `longitude` | float or null | precise coordinates (Phase 8) — **private**, never returned by `/api/donors/search`; only a rounded `distance_km` derived from them is exposed when a search supplies a reference point |
| `phone` | string | **private** — never returned by `/api/donors/search` |
| `availability` | bool, default true | donor-controlled toggle |
| `emergency_availability` | bool | opt-in for emergency contact |
| `last_donation_date` | date or null | drives eligibility calculation |
| `verification_status` | string enum | pending / verified / rejected |
| `preferred_hospitals` | array of strings | |
| `preferred_blood_banks` | array of strings | |
| `created_at`, `updated_at` | datetime | |

### Indexes
- `user_id`: unique
- `blood_group`, `city`: single-field, for search filtering
- compound `(availability, verification_status, blood_group)`: supports the search endpoint's default query pattern

### Privacy notes
- `/api/donors/search` (staff-only) returns `DonorPublicOut` — blood group, city, availability, eligibility, verification status. **No phone, no exact address, no name.** Verified by an automated test (`test_e2e_smoke.py`) that asserts `phone` is absent from search results.
- Only unverified→verified donors with `availability: true` are returned by search.
- Eligibility (`is_eligible`) is computed from `MIN_DONATION_INTERVAL_DAYS` (currently 90, in `app/core/rules.py`) — a fixed, admin-set constant, never an AI inference.

### Planned collections (not yet implemented)
None remaining — every collection the original spec named now has a
real implementation (see docs/architecture.md §18 for the honest
caveat list of what's tested vs. written-but-unverified).

## `audit_logs`
General staff/admin action trail — separate from `ai_tool_calls`,
which only covers AI-agent-initiated actions.

| Field | Type | Notes |
|---|---|---|
| `_id` | ObjectId | |
| `actor_id` | ObjectId | references `users._id` |
| `actor_role` | string | denormalized snapshot of the actor's role at the time |
| `action` | string, indexed | e.g. `donor.verify`, `request.fulfill`, `inventory.status_change` |
| `target_type` | string | e.g. `donor`, `blood_request`, `hospital`, `blood_bank`, `blood_inventory` |
| `target_id` | string | the affected document's id |
| `details` | object | action-specific extra context (e.g. `{"new_status": "verified"}`) |
| `created_at` | datetime | |

### Indexes
- `created_at desc`
- `action`
- compound `(target_type, target_id)`

### Coverage note
Logged from a single explicit helper call in each mutating endpoint
(`app/core/audit.py`), not a generic middleware — see
docs/architecture.md §15 for which actions are and aren't covered yet.

## `ai_tool_calls`
Every tool invocation attempt — allowed or blocked — regardless of
which session it came from. This is the real audit trail for AI
guardrail enforcement (Phase 10/11's "all AI actions must be logged"
requirement), not just a log of successful calls.

| Field | Type | Notes |
|---|---|---|
| `_id` | ObjectId | |
| `session_id` | ObjectId, indexed | references `ai_sessions._id` |
| `user_id` | ObjectId | who the session belonged to |
| `tool_name` | string, indexed | including names that were rejected for not being allowlisted |
| `input` | object | the raw tool input as requested |
| `success` | bool | |
| `error` | string or null | reason for failure, including "Tool not in allowlist — call blocked" |
| `created_at` | datetime | |

### Indexes
- compound `(session_id, created_at)`
- `tool_name` — supports auditing which tools are used/blocked most often

## `notifications`
| Field | Type | Notes |
|---|---|---|
| `_id` | ObjectId | |
| `user_id` | ObjectId, indexed | references `users._id` |
| `channel` | string enum | in_app / email / sms / push — see `app/models/notification.py` |
| `priority` | string enum | normal / high / emergency |
| `title`, `body` | string | for failed external sends, `body` has a `[delivery note: ...]` suffix explaining why |
| `status` | string enum | pending / sent / failed / read |
| `read` | bool | |
| `created_at` | datetime | |

### Indexes
- compound `(user_id, created_at desc)` — inbox listing
- compound `(user_id, read)` — unread-count queries

### Notes
- In-app notifications are always `status: sent` immediately — no
  external dependency.
- SMS/email attempts that fail due to missing provider credentials
  are stored as `status: failed` with the reason appended to `body`
  — never marked `sent` when nothing was actually delivered.
- `status` (delivery outcome) and `read` (has the user seen it) are
  independent fields — marking a notification read never changes its
  delivery status. `DeliveryStatus.READ` exists in the enum but is
  currently unused; it's reserved for a future case where "read"
  really is an external delivery outcome (e.g. an email open
  receipt), not today's in-app read state.

## `donor_responses`
Records each matching-engine run's candidates. Cleared and
regenerated every time `/api/requests/{id}/match` runs, so it
reflects the latest match, not a history (a `donor_responses` history
+ actual accept/reject tracking is Phase 6/9 work, once notifications
exist for donors to respond to).

| Field | Type | Notes |
|---|---|---|
| `_id` | ObjectId | |
| `request_id` | ObjectId, indexed | references `blood_requests._id` |
| `donor_id` | ObjectId | references `donors._id` |
| `blood_group`, `city`, `emergency_availability` | — | denormalized snapshot at match time |
| `distance_km` | float or null | real haversine distance (Phase 8) when both donor and request have coordinates; otherwise null |
| `eta_minutes` | int or null | naive straight-line estimate — not real routing, see `app/core/geo.py` |
| `score` | int | from `app/core/matching.py` |
| `status` | string | currently always `"matched"` — `contacted`/`accepted`/`rejected` land with the notification engine |
| `created_at` | datetime | |

### Indexes
- `request_id`, compound `(request_id, score desc)`
